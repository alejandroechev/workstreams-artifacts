Design note · 18 November 2026 · placeholders like ntfy.example.com and $NTFY_TOKEN stand in for your own values

Self-hosted ntfy: notifications that always arrive

How your own apps (Workstreams companion, the medical app, any script) can send you notifications that show up like WhatsApp or email, even with the apps closed, without Firebase or code changes on the phone.

In one minute
  1. On your server: one small Docker container (binwiederhier/ntfy) behind HTTPS, with users and access tokens.
  2. On your phone: install the ntfy app (Play Store or F-Droid), point it at your server, log in, subscribe to topics such as ws and medical. Nothing is installed in your own apps.
  3. How it delivers: the ntfy app keeps one connection open from the phone to your server (a background service). When a message arrives, the server pushes it down that connection and the app shows an Android notification. Self-hosted servers don't use Firebase for this.
  4. How your apps integrate: anything that can make an HTTPS request sends a notification: POST https://ntfy.example.com/<topic> with a token. The Click header makes a tap open your app.

2. What goes where

Server (once)

ntfy in Docker plus a reverse proxy (Caddy) for HTTPS. It can live on the same small VPS as other things you host, using about 15 MB of RAM. Set auth-default-access: deny-all so only your users and tokens can read or write.

Phone (once)

Install the ntfy app. Add your server URL, log in as your read-only user, and subscribe to your topics. Allow its notifications and turn off battery optimization for it. ntfy shows a quiet permanent "listening" notification; you can hide that one channel in Android settings.

Your apps (per sender)

No SDK and no phone-side change. The sender makes one HTTPS POST with a write-only token: Workstreams on the Mac, a Supabase function for the medical app, or a shell script. Add Click so a tap opens your app.

3. Sequence diagrams

On a phone, scroll the diagram sideways.

After setup, the phone holds an open, encrypted connection to your server. There's nothing to poll and nothing to schedule on the phone.

Workstreams already receives companion.send from agents. It would gain one setting (server URL, topic, token) and a POST to ntfy. The companion would gain a deep-link scheme (for example wscompanion://) so a tap opens the right session. Without one, use an https:// link, or leave Click out and open the app by hand.

Reminders must be sent by something that is always on, not by the phone app. A daily Supabase job reads the pickups and posts them. If a date changes, tomorrow's run simply sees the new date. Alternative: post with At: tomorrow, 9am when a pickup is saved, and ntfy holds the message (up to 3 days by default). But a scheduled message can't easily be cancelled if the pickup moves.

Only needed if notifications arrive late, for example on phones that kill background services aggressively, or on iOS. Your server sends ntfy.sh only a message ID and a hash of the topic. The phone then fetches the real message from your server.

4. How ntfy actually delivers

  1. The phone dials out. The ntfy app runs an Android background (foreground) service that opens a WebSocket to https://ntfy.example.com/ws,medical/ws. The phone starts the connection, so your server needs no access to the phone and no inbound port on it.
  2. A sender publishes. POST /ws with a token. ntfy checks the access list, stores the message in its cache (12 hours here) and pushes it to every open subscription for that topic.
  3. Android shows it. The ntfy app receives the message and posts a normal Android notification: sound, lock screen, priority, and the dot or count on the ntfy icon.
  4. Nothing is lost on a bad connection. When the phone reconnects (after the subway, airplane mode or a reboot), the app asks for messages since the last one it saw, and the server replays them from its cache.
  5. A tap opens your app. The Click URL opens a web page or your app's deep link. Actions can add buttons such as "Open session" or "Mark done".

5. Integration recipes

Server

docker-compose.yml
services:
  ntfy:
    image: binwiederhier/ntfy
    command: serve
    restart: unless-stopped
    volumes:
      - ./server.yml:/etc/ntfy/server.yml:ro
      - ./data:/var/lib/ntfy
    ports:
      - "127.0.0.1:2586:80"   # only Caddy reaches it
server.yml
base-url: "https://ntfy.example.com"
behind-proxy: true
cache-file: "/var/lib/ntfy/cache.db"
cache-duration: "12h"
auth-file: "/var/lib/ntfy/user.db"
auth-default-access: "deny-all"     # nobody without a user/token
# Optional: faster wake-up (iOS mostly). Sends only an ID + hash upstream.
# upstream-base-url: "https://ntfy.sh"
Caddyfile
ntfy.example.com {
    reverse_proxy 127.0.0.1:2586
}
Users, access and a token
docker compose exec ntfy ntfy user add phone        # you, on the phone
docker compose exec ntfy ntfy user add bots         # the senders
docker compose exec ntfy ntfy access phone ws ro
docker compose exec ntfy ntfy access phone medical ro
docker compose exec ntfy ntfy access bots  ws wo
docker compose exec ntfy ntfy access bots  medical wo
docker compose exec ntfy ntfy token add bots        # → token for the senders

Workstreams desktop

Rust — notify_phone()
// Workstreams desktop (Rust, reqwest): one POST, no SDK.
fn notify_phone(cfg: &NtfyConfig, title: &str, body: &str, click: &str) -> Result<(), String> {
    reqwest::blocking::Client::new()
        .post(format!("{}/{}", cfg.server, cfg.topic))   // https://ntfy.example.com/ws
        .bearer_auth(&cfg.token)                          // from the keychain, never in code
        .header("Title", title)
        .header("Click", click)                           // deep link into the companion
        .header("Markdown", "yes")
        .body(body.to_owned())
        .timeout(std::time::Duration::from_secs(10))
        .send()
        .and_then(|r| r.error_for_status())
        .map(|_| ())
        .map_err(|e| e.to_string())                       // caller retries later; never blocks the UI
}

Medical app (Supabase)

Edge Function — reminders
// Supabase Edge Function "reminders" (Deno), run daily by pg_cron.
Deno.serve(async () => {
  const due = await pickupsDue();          // your query: in 3 days / today / overdue
  for (const p of due) {
    await fetch(`${Deno.env.get("NTFY_URL")}/medical`, {
      method: "POST",
      headers: {
        Authorization: `Bearer ${Deno.env.get("NTFY_TOKEN")}`,   // Supabase secret
        Title: p.title,                    // e.g. "Pickup today"
        Tags: "pill",
        Click: "https://medical-app.example.com/",  // or the app's deep link
      },
      body: p.body,                        // keep health details minimal
    });
  }
  return new Response("ok");
});

6. Trade-offs

TopicSelf-hosted ntfyFCM inside each app
Arrives with apps closedYesYes
Work in your appsNone on the phone; one POST per senderPlugin, Firebase project and token handling per app
Google involvedNo (unless you enable the wake-up)Yes, every message goes through Firebase
Notification shows as"ntfy", with your title and tagsYour app, with its icon and badge
BatteryOne idle connection, small but not zeroShared with all apps
Phones that kill background appsDisable battery optimization for ntfy, or add the wake-upHandled by Google Play services
PrivacyContent stays on your serverPasses Google (can be encrypted end to end)
If your server is downNothing arrives; senders should retryGoogle's uptime

Later: notifications as your own app (UnifiedPush)

The ntfy app can also act as a UnifiedPush distributor. An app that includes the UnifiedPush connector library gets its own endpoint on your ntfy server, and messages arrive in that app, with its icon and its own unread number. That needs a small native (Kotlin) plugin in each Tauri app, so treat it as phase 2 once plain ntfy proves itself.

7. Checklist

  1. Point a DNS name at your VPS; run docker compose up -d with the files above.
  2. Create the phone and bots users, the access rules, and a token for bots.
  3. Install ntfy on the phone, add the server, log in, subscribe to ws and medical, and turn off battery optimization for it.
  4. Send the curl test with the phone locked and the app swiped away. It should arrive within a second or two.
  5. Workstreams: add the ntfy setting and post on companion.send. Optionally add a companion deep link.
  6. Medical app: add the Edge Function and a daily pg_cron job. Keep message bodies short, without health details.
